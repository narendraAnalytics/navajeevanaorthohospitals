1. Project Overview
OrthoAI is a full-stack Orthopedic Hospital platform combining a professional patient-facing website with an AI-powered support ticket triage agent. Built specifically for the Indian healthcare market - Andhra Pradesh focus - with Telugu/Hindi patient support in mind.
 
1.1  What This Project Solves
The Problem
Orthopedic hospitals in Andhra Pradesh (Apollo, KIMS, district hospitals) have front-desk staff drowning in repetitive patient queries - appointment bookings, test preparation instructions, report readiness, insurance questions.
An AI agent handling L1 queries automatically, and packaging complex cases for human staff with full context, directly reduces this load by 40-60%.

2. Architecture Overview
Five-layer architecture. Each layer has one job. Clean separation between UI, API gateway, agent brain, knowledge base, and data storage.
 
Layer 1 - Frontend (Next.js 15 on Vercel) 
Renders the hospital website, patient portal, and admin dashboard. Communicates with the backend via HTTP fetch() and Next.js Server Actions.
 
Layer 2 - API Gateway (FastAPI on AWS EC2 / Railway) 
Receives tickets from Next.js. Validates with Pydantic. Triggers LangGraph agent. Returns ticket ID instantly. Does NOT run agent logic itself - clean separation.
 
Layer 3 - Agent Brain (LangGraph StateGraph) 
5-node StateGraph: Intent Classifier ? RAG Knowledge Search ? Confidence Checker ? (Auto-Reply Writer | Escalation Packager) ? Database Writer. Uses Gemini API for LLM calls and ChromaDB for vector search.
 
Layer 4 - Database (Neon PostgreSQL + ChromaDB) 
Neon PostgreSQL: structured data - tickets, replies, escalations, agent logs. ChromaDB: knowledge base as vectors - FAQ docs, test prep guides, policy docs, past resolved tickets.

6. AI Agent - LangGraph Nodes
 
Flow:  Intent Classifier  ?  RAG Knowledge Search  ?  Confidence Checker  ?  (Auto-Reply | Escalation Packager)  ?  Database Writer 
Node 1 - Intent Classifier  (classifier.py)
Gemini reads the raw ticket text. Outputs structured classification - no auto-reply here, just labeling.
Output fieldValuescategoryappointment / test_prep / report / insurance / billing / post_surgery / emergency / otherurgencylow / medium / high / criticalsentimentcalm / anxious / frustrated / urgentkeywordsList of detected medical/contextual keywordslanguageenglish / telugu / hindi / mixed 
Node 2 - RAG Knowledge Search  (rag_search.py)
Converts ticket text to embedding vector. Searches ChromaDB for top-3 matching knowledge base documents. Returns documents with similarity scores.
Collections searched:
  appointment_faq  |  test_preparation  |  post_surgery_care  |  insurance_billing  |  past_tickets 
Node 3 - Confidence Checker  (confidence_check.py)
Evaluates the RAG results and ticket content to decide the routing path. This is the safety gate - especially important for a medical context.
CheckConditionActionConfidence scoreRAG score >= 80%Route to auto-replyConfidence scoreRAG score < 80%Route to escalationMedication keywordAny medicine name detectedALWAYS escalate - never auto-answer medication queriesPost-surgery symptomPain / swelling / fever / wound mentionedALWAYS escalate - safety ruleEmergency keywordChest pain / severe / can't breatheCRITICAL escalation - flag as urgentReport interpretationX-ray / MRI / report queryALWAYS escalate - only doctors interpret reportsAmount thresholdBilling dispute > ?10,000Escalate to billing managerFraud patternSuspicious keywords detectedFlag and escalate 
Node 4a - Auto-Reply Writer  (reply_writer.py)
Only runs when confidence >= 80% and no safety flags triggered. Uses Gemini to draft a personalized reply using RAG content, patient name, and ticket context. Self-evaluates quality before sending.
 
Node 4b - Escalation Packager  (escalation_packager.py)
Runs when confidence < 80% or any safety rule fires. Builds a full brief for the human support staff - they never see a ticket cold again.
Brief includes:
  Issue summary  |  Patient history  |  Similar past tickets  |  Suggested action  |  Tone note  |  Urgency flag

8. Database Schema
 
8.1  Neon PostgreSQL - Structured Data
 
tickets table
CREATE TABLE tickets (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id  TEXT NOT NULL,           -- Clerk user ID
  subject      TEXT NOT NULL,
  description  TEXT NOT NULL,
  category     TEXT,                    -- appointment/test_prep/etc
  urgency      TEXT DEFAULT 'low',      -- low/medium/high/critical
  sentiment    TEXT,
  status       TEXT DEFAULT 'received', -- received/processing/auto_resolved/escalated/resolved
  language     TEXT DEFAULT 'english',
  created_at   TIMESTAMPTZ DEFAULT NOW(),
  updated_at   TIMESTAMPTZ DEFAULT NOW()
);
 
replies table
CREATE TABLE replies (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  ticket_id  UUID REFERENCES tickets(id) ON DELETE CASCADE,
  content    TEXT NOT NULL,
  sent_by    TEXT NOT NULL,  -- 'agent' | 'human' | 'customer'
  sent_at    TIMESTAMPTZ DEFAULT NOW()
);
 
escalations table
CREATE TABLE escalations (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  ticket_id    UUID REFERENCES tickets(id) ON DELETE CASCADE,
  brief        TEXT NOT NULL,   -- Full agent brief for human staff
  assigned_to  TEXT,            -- Staff member name/ID
  resolved_at  TIMESTAMPTZ,
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
 
agent_logs table
CREATE TABLE agent_logs (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  ticket_id        UUID REFERENCES tickets(id),
  node_name        TEXT NOT NULL,    -- classifier/rag_search/etc
  decision         TEXT,
  confidence_score FLOAT,
  input_data       JSONB,
  output_data      JSONB,
  timestamp        TIMESTAMPTZ DEFAULT NOW()
);

13. Build Order - Start Here, Not Everywhere
Golden rule: Build backend first. Test it. Then build frontend. Never build both in parallel. 
Phase 1 - Backend Setup

21. Create .env file with all backend variables

23. Write the knowledge base .md docs (appointment_faq, test_prep, insurance, escalation_rules)
24. Write chroma_client.py - ChromaDB connection
25. Write loader.py - reads .md files, splits into chunks, loads into ChromaDB
26. Run seed_knowledge_base.py - test that ChromaDB is loaded
27. Write state.py - TicketState dataclass
28. Write each node file - classifier.py, rag_search.py, confidence_check.py, reply_writer.py, escalation_packager.py
29. Write graph.py and edges.py - wire nodes together
30. Write models/ticket.py and models/agent.py (Pydantic models)
31. Write routers/tickets.py and routers/admin.py
32. Write main.py - include routers, CORS, startup
33. Test with Swagger at http://localhost:8000/docs - submit a test ticket

15.3  Parallel Graph Flow - Fan-Out ? Fan-In
 
How LangGraph Parallel Execution Works 
LangGraph executes nodes that have no edges between them simultaneously within the same 'superstep'. When the Orchestrator fires three edges to three independent agents, all three run at the same time. The graph waits for all three to complete before moving to the fan-in node. This is the core performance gain.
 
Sequential (old):  Classify ? Safety ? RAG ? Evaluate ? Reply  =  ~9 seconds
Parallel (new):    Classify + Safety + RAG run simultaneously  =  ~3 seconds
Performance gain: 60-70% faster. Patients get replies in under 3 seconds. 
# Parallel graph structure (graph.py)
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import AsyncPostgresStore

graph = StateGraph(TicketState)

# --- Add all 8 nodes ---
graph.add_node("orchestrator",       orchestrator_node)
graph.add_node("intent_classifier",  intent_classifier_node)   # parallel branch 1
graph.add_node("safety_checker",     safety_checker_node)      # parallel branch 2
graph.add_node("rag_retriever",      rag_retriever_node)       # parallel branch 3
graph.add_node("confidence_eval",    confidence_evaluator_node)
graph.add_node("reply_writer",       reply_writer_node)
graph.add_node("escalation_packager",escalation_packager_node)
graph.add_node("memory_manager",     memory_manager_node)

# --- Fan-OUT: orchestrator ? 3 agents in parallel ---
graph.add_edge(START, "orchestrator")
graph.add_edge("orchestrator", "intent_classifier")  # fires simultaneously
graph.add_edge("orchestrator", "safety_checker")     # fires simultaneously
graph.add_edge("orchestrator", "rag_retriever")      # fires simultaneously

# --- Fan-IN: all 3 must complete before confidence_eval ---
graph.add_edge("intent_classifier", "confidence_eval")
graph.add_edge("safety_checker",    "confidence_eval")
graph.add_edge("rag_retriever",     "confidence_eval")

# --- Conditional edge: auto-reply OR escalate ---
graph.add_conditional_edges("confidence_eval", route_decision,
    {"auto_reply": "reply_writer", "escalate": "escalation_packager"})

# --- Both paths end at memory_manager ? END ---
graph.add_edge("reply_writer",        "memory_manager")
graph.add_edge("escalation_packager", "memory_manager")
graph.add_edge("memory_manager", END)

# --- Compile with checkpointer (short-term) + store (long-term) ---
app = graph.compile(checkpointer=PostgresSaver(conn), store=AsyncPostgresStore(conn))
 
15.4  Shared State Schema (state.py)
All 8 agents read from and write to one shared TicketState. Annotated list fields with operator.add reducer allow multiple parallel agents to write without overwriting each other.
 
# state.py - shared state for all agents
from typing import Annotated, Optional, List
from typing_extensions import TypedDict
from operator import add

class TicketState(TypedDict):
    # -- Input (set by FastAPI before graph starts) --------------
    ticket_id:          str
    customer_id:        str
    raw_text:           str            # patient's original message

    # -- Parallel agent outputs (reducer = add ? safe concurrent writes) --
    classifications:    Annotated[List[dict], add]  # from intent_classifier
    safety_flags:       Annotated[List[dict], add]  # from safety_checker
    rag_results:        Annotated[List[dict], add]  # from rag_retriever

    # -- Orchestrator outputs --------------------------------------
    urgency:            Optional[str]   # low/medium/high/critical
    language:           Optional[str]   # english/telugu/hindi

    # -- Confidence + routing -------------------------------------
    confidence_score:   Optional[float] # 0.0 to 1.0
    route_decision:     Optional[str]   # 'auto_reply' | 'escalate'
    escalation_reason:  Optional[str]   # why it was escalated

    # -- Final outputs --------------------------------------------
    reply_text:         Optional[str]   # auto-reply to send patient
    escalation_brief:   Optional[str]   # full brief for human staff
    final_status:       Optional[str]   # auto_resolved | escalated

    # -- Memory context (injected by memory_manager) --------------
    patient_history:    Optional[str]   # past tickets summary (long-term)
    conversation_turns: Annotated[List[dict], add]  # current session (short-term)

15.6  Memory Architecture - Short-Term + Long-Term
 
Short-Term Memory - PostgresSaver (per conversation thread) 
Stores the full agent state within a single support session. Survives server restarts. If a patient follows up on the same ticket, all prior context is available. Scoped by thread_id (= ticket_id in our system).
 
# Short-term memory setup (in main.py)
from langgraph.checkpoint.postgres import PostgresSaver
import asyncpg

conn = await asyncpg.connect(os.getenv("NEON_DB_URL"))
checkpointer = PostgresSaver(conn)
await checkpointer.setup()  # creates checkpoint tables in Neon automatically

# Invoke graph with thread_id = ticket_id (scopes memory to this ticket)
config = {"configurable": {"thread_id": ticket_id}}
result = await app.ainvoke(initial_state, config=config)
 
Long-Term Memory - AsyncPostgresStore (across all sessions, per patient) 
Stores extracted facts about the patient that persist ACROSS all their tickets. Keyed by customer_id (Clerk user ID). The Memory Manager agent extracts and writes facts here at the end of every ticket processing.
 
# Long-term memory setup (in main.py)
from langgraph.store.postgres import AsyncPostgresStore

store = AsyncPostgresStore(conn)
await store.setup()  # creates store tables in Neon automatically

# Compile graph with BOTH memory layers
app = graph.compile(checkpointer=checkpointer, store=store)
 
# memory_manager.py - how facts are written to long-term store
async def memory_manager_node(state: TicketState, store: AsyncPostgresStore):
    customer_id = state["customer_id"]
    namespace = ("patient_facts", customer_id)  # keyed by patient

    # Extract facts from this ticket using Gemini Flash
    facts = await llm_flash.ainvoke([
        SystemMessage(content="Extract medical facts, preferences, and history from this ticket. Output JSON only."),
        HumanMessage(content=state["raw_text"])
    ])

    # Write to long-term store (merges with existing patient facts)
    await store.aput(namespace, key="ticket_" + state["ticket_id"], value=facts)

    return {"final_status": state["route_decision"]}
